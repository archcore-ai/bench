# Токенный бенчмарк Archcore — полный разбор

[English](ANALYSIS.md) · **Русский**

> **Цель:** воспроизводимо установить, экономит ли Archcore токены на реальной кодовой базе
> при фиксированной планке качества — и если да, то где именно. Здесь приведены все числа и
> честные выводы, включая те утверждения, которые делать нельзя.

Модель: **claude-sonnet-5** (`--model sonnet`). Счётчики токенов точные, из
`claude -p --output-format json` (`.usage`).

**Замерено 12.08.2026** — archcore CLI **v0.7.0**, плагин **v0.7.1**, Claude Code **2.1.228**.
Предыдущий прогон v1 (31.05.2026): archcore v0.3.6, плагин v0.6.x, Claude Code 2.1.16x, та же
модель. Оба прогона лежат в репозитории (`results_v1.csv` / `results_v2.csv`); все таблицы
ниже показывают v1 → v2.

## Выводы

### Что именно измерено

Одна вещь: сколько токенов тратит агент, чтобы найти нужный факт в документации проекта.
Качество ответов не измерялось. Все способы доступа отвечают одинаково верно, это заложено в
конструкцию теста, чтобы сравнивать цену при равном результате. Про пользу для качества ответов
бенчмарк не говорит ничего.

### Что влияет на счёт сильнее всего

| Что меняем | Во сколько раз меняется цена | В деньгах |
|---|---|---|
| Задать 8 вопросов в одной сессии вместо 8 отдельных | **6.2×** | $0.462 → $0.074 за вопрос |
| Не держать всю документацию в `CLAUDE.md` (1 документ против 320) | 5.6× | $0.139 → $0.784 за задачу |
| Сменить способ поиска на лучший (при 80 документах) | **1.3×** | $0.608 → $0.470 за задачу |

Способ поиска влияет на счёт слабее всего. Сначала имеет смысл менять то, что в таблице выше.

Батчинг измерялся только на Archcore, у остальных способов его не проверяли. Механизм за ним
общий: фиксированные накладные сессии делятся на все её вопросы.

### Брать ли Archcore ради экономии

| Ситуация | Ответ |
|---|---|
| Документов меньше 50 | Нет. `CLAUDE.md` или обычный grep дешевле. |
| Документов больше 100-150 | Да. Дешевле всех остальных способов. |
| Где-то посередине | Разница в пределах погрешности. |
| Важен худший случай, а не типичный | Да, от 80 документов. Единственный способ, который ни разу не сорвался: 0 срывов за 60 прогонов против 22 у grep. |
| Важна скорость ответа | Да. 8.8 секунды в среднем против 16.3 у grep, в худшем случае 16.5 против 93. |

По типичной задаче grep дешевле в 2.5 раза ($0.178 против $0.437). По средней цене Archcore
дешевле на 23% ($0.470 против $0.608). Обе цифры верны и посчитаны по одним и тем же 60
прогонам. Grep в двух случаях из трёх находит файл сразу, а в оставшихся уходит в долгий перебор
и стоит до $2.40 за задачу.

### Стал ли Archcore дешевле в v0.7

Нет. Он обрабатывал 142k токенов в мае и 144k сейчас, по $0.432 и $0.437. `mode=full` сократил
число обращений с 5 до 3 и убрал 33% времени ожидания, но не токены.

Место Archcore в рейтинге при этом изменилось: в мае он был самым дорогим способом, сейчас самый
дешёвый. Причина не в нём. Claude Code 2.1.228 испортил `Grep` и `Read` на больших базах, и
подорожали конкуренты, в 2.4-3.5 раза.

### Снижает ли стоимость плагин

Нет. На всех четырёх размерах батча число обращений совпадает, разница в цене на уровне
случайности. Плагин нужен для команд `document`, `plan` и `review`, а не для удешевления поиска.

## 0. Что изменилось с v1

Сдвинулись три вещи одновременно, и только одна из них — Archcore.

| №   | Изменение                                                | Влияние на числа                                                                           |
| --- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 1   | **`search_documents(mode=full)` доехал** в CLI v0.7.0    | Арм C: 5 turns → **3 turns**. Стоимость в токенах не изменилась. Латентность −33%.         |
| 2   | **`/archcore:context` удалён** в плагине v0.7            | Весь плагинный бенчмарк v1 мерил механизм, которого больше нет. Пересобран с нуля — §3.    |
| 3   | **Claude Code 2.1.228 испортил Grep/Read на больших KB** | Бейзлайны B2/B3 подорожали в 2.4–3.5× и стали бимодальными. **Это не улучшение Archcore.** |

Между v1 и v2 ранжирование переворачивается — Archcore из самого дорогого арма становится
самым дешёвым на workload-сьюте. **Причина — изменение №3, а не №1 и не №2.** Собственная
стоимость Archcore не сдвинулась: арм C обработал 142k токенов контекста в v1 и 144k в v2.

## 2. CLI-бенчмарк

### 2.1 Армы

Все армы делят один исходный субстрат (`go-chi/chi`) и одни и те же инструменты
`Read/Grep/Glob`. B1/B2/B3/C несут **идентичные документы** — различается только способ
доступа. Арм A — это пол.

| Арм                 | Знание                                                           | Индекс     | Доп. инструменты | Моделирует                          |
| ------------------- | ---------------------------------------------------------------- | ---------- | ---------------- | ----------------------------------- |
| **A — cold**        | нет                                                              | —          | —                | вообще без документов               |
| **B1 — preload**    | все N документов в `CLAUDE.md`                                   | н/п        | —                | «запихнуть всё в контекст»          |
| **B2 — index+grep** | N документов файлами + индекс в `CLAUDE.md` (пути+темы, без тел) | да         | —                | документы-файлы с курируемой картой |
| **B3 — blind grep** | те же N документов файлами, без индекса                          | нет        | —                | документы-файлы, агент ищет Grep'ом |
| **C — archcore**    | те же N документов файлами                                       | нет (авто) | archcore MCP     | извлечение через Archcore           |

B2 и B3 присутствуют оба, потому что реальный конкурент Archcore — не только наивный preload,
но и «просто держать markdown в репозитории». B2 даёт этому подходу идеальный бесплатный
индекс (самый тяжёлый бейзлайн). B3 индекс убирает — агент обязан пользоваться встроенным
Grep. Сравнение C против B3 изолирует вопрос «бьёт ли MCP-поиск Archcore обычный Grep по тем
же файлам?»

### 2.2 База знаний и контроль качества

320 синтетических документов по 5 доменам (middleware, routing, errors, logging, testing),
**~550 токенов каждый** (реалистичный ADR/rule: секции Context / Decision / Consequences /
Alternatives / Example / References). Каждый документ кодирует одну нормативную конвенцию,
ответ на которую — **произвольный токен, закопанный в секции Decision**. В заголовке и в
поисковой выдержке он не появляется, поэтому результата поиска недостаточно — агент обязан
открыть документ.

Оценка по точному совпадению токена: правильный ответ означает, что знание было извлечено,
а не угадано.

### 2.3 Метрика стоимости

Две метрики, обе реконструируются из ответа API независимо от порядка прогонов. **Каждый
вывод ниже проверен по обеим**; где они расходятся — это сказано явно.

- **cold:** `ctx_in × $3/M + output × $15/M`, где `ctx_in = input + cache_creation + cache_read`.
  Без модели turns, без допущений. Равна тому, что списала бы некэшированная сессия — каждый
  ход агента переотправляет весь контекст свежим вводом. Моделирует мультисессионный режим.
- **realistic:** моделирует свежую сессию на задачу с кэшем внутри задачи.
  ```
  prefix    = ctx_in / num_turns
  realistic = prefix × (1.25 + 0.10 × (turns − 1)) × $3/M + output × $15/M
  ```

> **Оговорка, добавленная в v2 — realistic штрафует сокращение turns.** При фиксированном
> `ctx_in` _меньшее_ число turns оценивается как _более дорогое_: формула предполагает, что
> контекст размазан по ходам и дисконтирован по ставке cache-read. Когда `mode=full` срезал
> арм C с 5 turns до 3 при том же объёме токенов, realistic-стоимость C выросла
> $0.147 → $0.212, а cold осталась плоской ($0.432 → $0.437). Это артефакт модели, а не
> подорожание. Для армов с сильно разным числом turns предпочитайте cold.

**Медиана против среднего.** В v1 отчёт строился на медианах. В v2 grep-армы стали бимодальными
(§2.6), и медиана прячет ровно то поведение, которое определяет стоимость сьюта. Приводятся
обе; среднее — это то число, которое попадает в счёт.

### 2.4 Результаты crossover

Фиксированная якорная задача; развёртка размера KB N ∈ {1, 20, 80, 160, 320}; 5 армов;
5 трайлов на ячейку.

**cold $/задача — медиана (v1 → v2):**

| N   | A cold          | B1 preload        | B2 index+grep | B3 blind grep     | **C archcore**    |
| --- | --------------- | ----------------- | ------------- | ----------------- | ----------------- |
| 1   | 0.832 → 0.458 ✗ | 0.081 → **0.139** | 0.164 → 0.569 | 0.244 → 0.174     | 0.433 → 0.434     |
| 20  | 0.884 → 0.312 ✗ | 0.107 → **0.175** | 0.166 → 0.427 | 0.246 → 0.177     | 0.432 → 0.434     |
| 80  | 0.857 → 0.443 ✗ | 0.190 → 0.290     | 0.175 → 0.297 | 0.252 → **0.184** | 0.432 → 0.441     |
| 160 | 0.795 → 0.438 ✗ | 0.309 → 0.455     | 0.191 → 0.648 | 0.254 → 1.298     | 0.355 → **0.441** |
| 320 | 1.078 → 0.591 ✗ | 0.545 → 0.784     | 0.224 → 0.741 | 0.254 → 1.350     | 0.432 → **0.435** |

✗ = задача провалена (у арма A нет доступа к знанию; 0/25). Жирным — самый дешёвый из
проходящих армов.

**Арм C плоский и детерминированный.** Во всех 25 crossover-прогонах он использовал
**ровно 3 turns** и 143–146k токенов контекста — каждый трайл, каждый размер KB. Больше
ни один арм не стабилен:

| Арм            | Токены контекста по трайлам (k), N=160 | N=320                     |
| -------------- | -------------------------------------- | ------------------------- |
| **C archcore** | `143, 144, 146, 146, 146`              | `143, 143, 144, 144, 146` |
| B1 preload     | `152, 152, 152, 152, 152`              | `261, 261, 261, 261, 261` |
| B2 index+grep  | `213, 213, 213, 264, 335`              | `121, 244, 245, 304`      |
| B3 blind grep  | `51, 60, 424, 555, 919`                | `50, 109, 438, 561, 831`  |

B1 тоже стабилен — это preload, его стоимость детерминирована по построению и линейна по N.

**Точки перелома — N, при котором C становится дешевле:**

| Сравнение                | метрика cold | метрика realistic |
| ------------------------ | ------------ | ----------------- |
| C против B1 (preload)    | N ≈ 151      | N ≈ 12            |
| C против B2 (index+grep) | N ≈ 106      | N ≈ 95            |
| C против B3 (blind grep) | N ≈ 94       | N ≈ 86            |

Метрики резко расходятся на B1 (12 против 151), потому что B1 отвечает за один ход, а C за
три — ровно тот случай, где модель turns доминирует. Приводите диапазон, а не одно число.

**Про окно контекста.** В v1 переполнение при preload отмечалось как риск. На окне sonnet-5
в 1M это неактуально: B1 на 320 документах занимает 261k токенов — 26% окна. Проблема
preload теперь чисто стоимостная.

### 2.5 Результаты workload

Фиксированный N=80; 20 задач по всем 5 доменам; армы B2/B3/C; 3 трайла = 60 замеров на арм.

**Распределение стоимости задачи (v2, cold):**

| Арм            | n   | медиана   | **среднее** | min   | max   | max/мед | прогонов >2× мед | turns | pass  |
| -------------- | --- | --------- | ----------- | ----- | ----- | ------- | ---------------- | ----- | ----- |
| B3 blind grep  | 60  | **0.178** | 0.608       | 0.143 | 2.400 | 13.5×   | **22/60**        | 1     | 60/60 |
| B2 index+grep  | 60  | 0.597     | 0.607       | 0.295 | 1.224 | 2.0×    | 1/60             | 4     | 60/60 |
| **C archcore** | 60  | 0.437     | **0.470**   | 0.433 | 0.635 | 1.5×    | **0/60**         | 3     | 60/60 |

**По медиане blind grep дешевле Archcore в 2.5 раза. По среднему Archcore дешевле обоих
бейзлайнов на 23%.** Оба утверждения истинны и описывают одни и те же 60 прогонов. Разница
между ними — это хвост.

**Итог по сьюту — стоимость одного прохода всех 20 задач:**

| Арм            | cold, v1 | cold, v2 по медиане | **cold, v2 по среднему** | realistic, v2 по среднему |
| -------------- | -------- | ------------------- | ------------------------ | ------------------------- |
| B2 index+grep  | 3.50     | 11.95               | 12.14                    | 4.72                      |
| B3 blind grep  | 5.04     | 3.56                | 12.17                    | 5.05                      |
| **C archcore** | 8.64     | 8.73                | **9.40**                 | **4.31**                  |

Итоги по медиане предполагают, что каждая задача типичная — а это ровно то допущение, которое
бимодальный арм нарушает. **По обеим метрикам, по ожидаемой стоимости, арм C — самый дешёвый.**
В v1 он был самым дорогим.

**Латентность (секунд на задачу, v2):**

| Арм            | медиана | среднее | max      |
| -------------- | ------- | ------- | -------- |
| B3 blind grep  | **2.6** | 16.3    | **93.4** |
| B2 index+grep  | 12.3    | 12.6    | 26.8     |
| **C archcore** | 8.1     | **8.8** | **16.5** |

Форма та же, что и по стоимости: grep быстрее всех, когда срабатывает, и катастрофичен, когда нет.

### 2.6 Механика

**Почему B3 разнесло: он стал бимодальным.** Слепой grep теперь распадается на две популяции:

| Популяция             | Доля | Контекст | cold $ | Время |
| --------------------- | ---- | -------- | ------ | ----- |
| «повезло» (≤2 turns)  | 65%  | 50k      | 0.151  | 2 с   |
| «сорвался» (>2 turns) | 35%  | 438k     | 1.338  | 32 с  |

В v1 такого расщепления не было — B3 выдавал 83k токенов за 3 turns практически на каждом
прогоне. Под Claude Code 2.1.228 агент либо сразу попадает в нужный файл, либо расползается
по десяткам кандидатов. **B2 деградировал так же, хотя несёт идеальный бесплатный индекс** —
57k токенов / 2 turns в v1 превратились в 98–246k / 2–5 turns при N=80. То, что регрессировал
арм с индексом, — самое ясное свидетельство: причина в поведении хоста, а не в стратегии
извлечения.

**Что на самом деле дал `mode=full`.** Арм C, v1 → v2, workload:

|             | turns | контекст | cold $ | время     | вывод    |
| ----------- | ----- | -------- | ------ | --------- | -------- |
| v1 (v0.3.6) | 5     | 142k     | 0.432  | 12.0 с    | 396 ток. |
| v2 (v0.7.0) | **3** | 144k     | 0.437  | **8.1 с** | 276 ток. |

`search_documents(mode=full)` возвращает тело найденного документа сразу, убирая обращение к
`get_document` и один ход ленивой загрузки схемы `ToolSearch`. **Он купил латентность и число
turns, но не токены: тот же контекст обрабатывается в обоих случаях.

**Инфляция бейзлайнов системная.** B1 preload при N=1 вырос с 27k до 46k токенов контекста;
системный промпт Claude Code между 2.1.16x и 2.1.228 прибавил примерно 19k токенов. Это
константа по армам, в сравнениях она сокращается, но абсолютные стоимости v1 и v2
сопоставлять напрямую нельзя — сопоставимы только ранжирования внутри прогона.

**Изменение методики: `MAXTURNS` 12 → 20.** В v1 ни один арм не превышал 12 turns. В v2 два
прогона B3 потребовали 15 и 17, так что потолок в 12 обрезал бы их и занизил стоимость B3.

## 3. Плагинный бенчмарк

### 3.1 Бенчмарк v1 мерил механизм, которого больше нет

До плагина v0.6 промпт арма D открывался строкой `/archcore:context <domain>` — явной
командой, которая заранее втягивала документы области в сессию. **Плагин v0.7 её удалил.**
Команды теперь `document` / `init` / `plan` / `review`, и ни одна из них не извлекает.

Контекст приходит иначе: **хук SessionStart** автоматически инжектирует в каждую сессию
заголовок корпуса — счётчики документов, ветку, словарь тегов и указатель на MCP-инструменты.
Примерно 150 токенов и **без тел документов**:

```
[Archcore — Git-native context for AI coding agents]
You have MCP tools available: list_documents, get_document, search_documents, ...
CORPUS: 80 documents — knowledge 80 · accepted 80
BRANCH: main
EXISTING TAGS: errors, logging, middleware, routing, testing, error, test, log, ...
```

Это подсказка маршрута, а не preload. Поэтому §3 пересобран с нуля; `scale/run_plugin.sh`
оставлен без изменений, чтобы числа v1 остались воспроизводимыми, а новый драйвер —
`scale/run_plugin_v7.sh`.

### 3.2 Новая схема

- **Арм D:** `--plugin-dir …/plugins/archcore` → инжекция SessionStart + скиллы + хуки
- **Арм C:** без плагина, тот же MCP-сервер archcore (контроль)
- **Промпт у обоих армов идентичен.** В v0.7 вклад плагина стал ambient, а не промптовым,
  поэтому любая дельта атрибутируется ему одному.

Проверено до замеров: хук действительно срабатывает в headless-режиме `-p` (D дословно цитирует
строку `CORPUS`, C отвечает `NONE`), так что контроль чистый и глобально установленный плагин
в C не протекает.

KB — v0.7-совместимая копия арма N=80: четыре тега-акронима в верхнем регистре понижены, чтобы
`archcore status` отдавал чистый проект. Все 80 fact-токенов и все 40 токенов plugin-задач
проверены на месте; диff против CLI-арма — 8 строк тегов. Сложность извлечения не изменилась.

Схема: 3 трайла × 5 доменов × 4 размера батча (N ∈ {1,2,4,8}) × 2 арма = **120 замеров**,
0 ошибок, 100% pass.

### 3.3 Результат: плагин не влияет на стоимость извлечения измеримым образом

| Батч | Арм   | cold $/вопрос (медиана) | среднее | [min–max]     | turns | контекст |
| ---- | ----- | ----------------------- | ------- | ------------- | ----- | -------- |
| 1    | C     | 0.4606                  | 0.4625  | [0.447–0.493] | 3     | 151k     |

**Инжектируемый заголовок корпуса не меняет то, как модель извлекает.** Он сообщает, что
существует; модель всё равно проходит тот же цикл «искать и читать».

### 3.4 Батчинг сессий работает — но заслуги плагина в этом не было никогда

| Вопросов на сессию | cold $/вопрос (среднее, оба арма) | к N=1    |
| ------------------ | --------------------------------- | -------- |
| 1                  | 0.461                             | база     |
| 2                  | 0.248                             | −46%     |
| 4                  | 0.132                             | −71%     |
| 8                  | 0.074                             | **−84%** |

Фиксированные накладные сессии — схемы MCP, системный промпт, контекст исходников — списываются
один раз и амортизируются по всем вопросам сессии. **Оба арма получают это одинаково.** В v1
эта экономия была изложена в плагинном разделе и читалась как выигрыш плагина; на деле это
свойство батчинга вопросов в одну сессию, доступное и без плагина.

## 4. Сравнение: CLI против плагина

|                    | CLI, 1 вопрос/сессия | Батч, 4 в/сессия | Батч, 8 в/сессия |
| ------------------ | -------------------- | ---------------- | ---------------- |
| cold $/вопрос      | 0.461                | 0.132            | 0.074            |
| Turns              | 3                    | 6                | 10               |

**Батчите, когда можете:** 4+ вопроса об одной области в одной сессии дают 71–84% экономии на
вопрос. **Ставьте плагин ради того, чем он теперь является** — сценарии `document` / `plan` /
`review` и хуки авторинга, — а не ради экономики извлечения, где он нейтрален.

## 5. Что показали данные и чего они не показывают

### Подтверждено замерами

- Стоимость извлечения Archcore плоская и детерминированная по мере роста KB: 3 turns и
  143–146k токенов контекста на любом размере от 1 до 320 документов, 25 прогонов. Самый
  надёжно обеспеченный результат здесь.
- На сьюте из 20 задач при 80 документах у Archcore самая низкая ожидаемая стоимость среди всех
  способов, на 23% ниже обоих grep-бейзлайнов, потому что у него нет хвоста: 0 прогонов из 60
  выше 2× медианы против 22 из 60 у слепого grep. Держится по обеим метрикам.
- Archcore ответил верно на все задачи при любом размере KB и в любых условиях.
- Preload через `CLAUDE.md` растёт линейно по размеру KB, Archcore не растёт. Примерно со
  100–150 документов Archcore дешевле. Метрики расходятся в точной точке перелома, поэтому
  честная форма этого утверждения — диапазон (§2.4).
- Батчинг 4–8 вопросов об одной области в одну сессию срезает стоимость вопроса на 71–84%,
  на выборке в 120 замеров.

### Не подтверждено

- **Archcore не подешевел в v0.7.** Его стоимость прошла путь от 142k до 144k токенов, с $0.432
  до $0.437. Ранжирование изменилось из-за регресса бейзлайнов под Claude Code 2.1.228.
- **Archcore не бьёт grep на типичной задаче.** По медиане слепой grep дешевле в 2.5 раза при
  80 документах. Преимущество Archcore лежит в ожидаемой стоимости и в разбросе.
- **`mode=full` не экономит токены.** Он экономит обращение и 33% времени ожидания при том же
  объёме токенов.
- **Плагин не снижает стоимость извлечения.** Четыре размера батча, идентичное число turns,
  парные победы на уровне случайности, дельта контекста в шуме. Оба плагинных утверждения v1
  (на 10% дешевле при N=4, более узкий разброс) описывали `/archcore:context`, которого больше нет.

### Вообще за рамками бенчмарка

- **Качество ответов.** Каждый способ, несущий знание, отвечает верно по построению теста, чтобы
  сравнивать цену при равном результате. Ничто здесь не показывает, делает ли Archcore ответы
  лучше, только сколько стоит извлечение.
- **Рассуждение по нескольким документам, связи, дрейф, governance.** Все задачи однофактовые.
  То, ради чего Archcore в основном и берут, здесь не задействовано.
- **Перенос на реальные базы знаний.** Answer-токены намеренно невыводимы, а это тяжелее
  большинства реальных запросов, где частичный контекст уже помогает.
- **Устойчивость между версиями хоста.** Любое сравнение с бейзлайнами зависит от поведения
  Grep/Read в Claude Code, которое существенно изменилось внутри одного минорного диапазона.

## 6. Оговорки

1. **Синтетическая KB с невыводимыми answer-токенами** — задача тяжелее большинства реальных
   запросов. На реальных KB, где ответ смежен теме, ранжирование армов может отличаться.
2. **Одна модель (sonnet-5), один репозиторий (chi).** Только однофактовые задачи-конвенции;
   ни многодокументного синтеза, ни связей Archcore, ни governance-функций.
3. **Индекс B2 считается идеально поддерживаемым и бесплатным** — самый тяжёлый бейзлайн для
   Archcore. В реальности поддержка курируемого индекса стоит денег, и бенчмарк это не оценивает.
4. **Чувствительность к версии хоста стала эффектом первого порядка.** Между Claude Code
   2.1.16x и 2.1.228 grep-бейзлайны изменились в стоимости в 2.4–3.5× без изменения KB, задачи
   и модели. Считайте любое межармовое число действительным только для указанной версии хоста.
5. **5 трайлов на ячейку crossover — мало для бимодальных армов.** Надёжная база для утверждений
   о распределении — фаза workload (60 на арм); crossover задаёт направление.
6. **Метрика realistic штрафует сокращение turns** (§2.3) — при разном числе turns берите cold.
7. **Абсолютные стоимости v1 и v2 несопоставимы** — системный промпт хоста вырос примерно на
   19k токенов. Сравнивайте ранжирования внутри прогона, а не долларовые величины между прогонами.
